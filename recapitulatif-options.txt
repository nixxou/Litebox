================================================================================
 RÉCAPITULATIF DES OPTIONS ET FICHIERS DE DONNÉES — LiteBox 0.8.9
================================================================================

Tout ce que LiteBox écrit vit sous <LaunchBox>\Core\litebox\ (LiteBoxPaths.Data).
Rien n'est écrit ailleurs, à trois exceptions près : les XML LaunchBox (Data\*.xml,
champs du schéma LB uniquement), les flux ADS NTFS attachés aux fichiers d'images
(§6), et ThirdParty\ (outils natifs déployés par NativeInstaller).

Règles de rangement (décidées avec le chantier "standardisation du stockage") :

  LiteBox.ini          scalaires plats : bootstrap, toggles globaux, défauts
                       globaux gameplay, état d'interface (fenêtre, colonnes…)
  *.json               config STRUCTURÉE par fonctionnalité (listes, objets) —
                       créés uniquement au premier usage de la fonctionnalité
  litebox-options.db   données PAR-ENTITÉ (jeu / émulateur / plateforme), clés
                       "problématiques" routées selon la version LB, clés Hot
  dbs dédiées          état durable à fort volume (historique, cache d'archives)
  cache\               tout ce qui est reconstructible (thumbs, GLB 3D, badges…)
  logs *.log           diagnostic, purgeables à tout moment

Un réglage GLOBAL plat ne va JAMAIS dans la base ; une donnée par-entité ne va
JAMAIS dans l'ini. Les fichiers de config n'apparaissent qu'à l'usage : une
install fraîche ne contient que LiteBox.ini, les dbs et cache\.

================================================================================
 1. LiteBox.ini — configuration principale (clé=valeur, sections [Nom])
================================================================================

Créé au premier lancement avec un en-tête commenté. Écriture en "merge-save" :
chaque instance ne réécrit que les clés qu'elle a modifiées (deux fenêtres
ouvertes ne s'écrasent pas). Exemple d'extrait réel :

    ReadOnly=false
    UseGameCache=true
    SmartCaptureEnabled=true
    StartupStayOnTop.Emulator=true
    Col.title=320,1,0
    [Base]
    AutoUpdateDb=true

Accès code : LiteBoxConfig.LoadForExe().Get/GetBool/GetInt, GetSec pour les
sections. Exemple type (Host/LiteBoxConfig.cs) :

    public bool UseGameCache { get => GetBool("UseGameCache", true);
                               set => SetBool("UseGameCache", value); }

 2. Fichiers JSON — un par fonctionnalité, créés au premier usage

--------------------------------------------------------------------------------
 media-layout.json — pipeline d'images du panneau de détail
--------------------------------------------------------------------------------
Écrit à l'apply des options Display → Right panel (MediaLayout.Save()).
Décrit, PAR VUE (liste / poster), l'image immédiate puis la liste post-load.

    { "ImmediateList": "Front", "ImmediatePoster": "Model3d",
      "Immediate3dFallback": "Front", "PosterIndependent": false,
      "PostLoad": [ { "Sel": "Front", "Count": 1 },
                    { "Sel": "Model3d", "Count": 1 },
                    { "Sel": "Screenshots", "Count": 5 } ] }

Clés d'une entrée PostLoad (Host/Media/MediaLayout.cs) : Sel = famille, type
exact (ExactType), ou la pseudo-famille "Model3d" (le modèle 3D de boîte) ;
Count = nombre max ; Mode auto|all ; WRegion/WType/WNumeric/WAspect = poids de
tri ; Cumulative(+Depth) = accumulation multi-entrées ; IgnoreGameRegion /
AllRegions = élargissement des régions. Le hash MD5 de cette config sert de clé
au cache anti-doublons (ADS :lb.dupcheck).

VALIDITÉ DU MODÈLE 3D — décide si un jeu MÉRITE un modèle (affichage ET bake).
Réglée dans Display → GENERAL, pas Right panel : elle dépasse le panneau droit,
conditionnant aussi le bake, la génération en masse et l'index des clés.
STOCKÉE DANS LiteBox.ini, PAS dans ce json — ce sont des globales PLATES, et le
json n'est justifié que par la LISTE PostLoad (même critère que youtube.json).
Clés : Model3dRequireBack / Model3dRequireSpine / Model3dRequireBothScans /
Model3dAcceptFullScan (toutes false par défaut, écrites dans le template ini).
Le FRONT est toujours requis (sans lui la boîte porte le placeholder "NoImage"
de LaunchBox) ; RequireBack/RequireSpine ajoutent des exigences ; si les DEUX
sont demandées, RequireBothScans choisit entre « les deux » (true) et « l'une ou
l'autre » (false). AcceptFullScan = une planche Box - Full suffit à elle seule —
la case reste cochable même si le mode full-scan paraît désactivé globalement,
car ce mode se règle aussi par plateforme et par jeu : l'arbitrage se fait par
jeu à la résolution. La règle n'entre PAS dans la clé de cache (elle ne change
pas le rendu) : la durcir ne re-bake donc rien. Lecture via Model3dOptions =
SNAPSHOT en mémoire, aucune I/O ini à l'usage courant (il sert aussi
TargetAspect, qui re-parsait l'ini une fois PAR JEU résolu) ; l'apply invalide
le snapshot et relance le calcul d'index (Model3dKeyIndex.KickAll).

La pseudo-famille "Video" : les vidéos du jeu deviennent des éléments de la
liste, comme les images. "Video" prend TOUS les types dans l'ordre (racine =
vidéo principale, puis Trailer, Theme, Marquee, Recordings) ; "Video:<SousDoss>"
n'en prend qu'un (entrées « Video · Trailer », etc. dans l'éditeur). Ces types
sont les SOUS-DOSSIERS de <LB>\Videos\<plateforme>\. La vignette est la frame
extraite à 20 % (VideoThumbnailer, cache disque) : l'extraction est LENTE, donc
elle n'est JAMAIS faite sur le chemin d'affichage — la case reste noire et un
worker dédié récupère les frames manquantes APRÈS le délai post-load, une vidéo
à la fois, en s'arrêtant net (entre deux vidéos, sans rien avorter) dès que la
sélection change. Le ▶ est DESSINÉ sur la vignette, jamais incrusté dans le
fichier de cache. En média principal, la vidéo est jouée par libvlc dans la zone
image ; les contrôles (play/pause, seek, temps, muet) n'apparaissent qu'au
SURVOL ; sans autoplay (VideoAutoplay, §1.2) la frame reste affichée avec un ▶.
L'anti-doublons l'ignore dans les deux sens.

La pseudo-famille "Model3d" : l'entrée n'existe que si le jeu PEUT avoir un
modèle (règle de validité ci-dessus) ; elle est IGNORÉE par
l'anti-doublons (dans les deux sens) ; sa vignette porte un badge « 3D » ; en
main box elle affiche la PNG du cache GLB puis bascule sur le viewport 3D
interactif (orbite). En IMAGE IMMÉDIATE ("ImmediateList"/"ImmediatePoster" =
"Model3d") : PNG du cache uniquement — jamais de bake ni de viewport à
l'instant ; si le modèle n'est pas bakable ou pas encore en cache, la famille
"Immediate3dFallback" (défaut Front) est affichée à la place.
Cas d'usage : Front en immédiat, puis le modèle 3D en 2e vignette post-load.

 youtube.json — intégration YouTube / yt-dlp

 ra-panel.json — RetroAchievements (compte + activation par plateforme)
--------------------------------------------------------------------------------
Écrit à la connexion RA et à chaque changement dans Options → LB·Integrations →
RetroAchievements (RaPanelSupport.Persist).

    { "mode": "onselect", "enabled": { "Nintendo 64": true },
      "hasherPath": "", "refreshHours": 0,
      "user": "…", "passwordBlob": "<chiffré>", "apiKey": "…",
      "tokenObtainedUtc": "2026-07-27T…", "renewTokenEveryDays": 0 }

mode : quand résoudre le hash (onselect…) ; enabled : diff par plateforme par

--------------------------------------------------------------------------------
 rom-profiles.json — profils de l'extracteur de ROMs
--------------------------------------------------------------------------------
Écrit quand on modifie un profil (Options → modules Rom). Un profil par couple
(émulateur, plateforme), "All" = générique (Host/Rom/RomConfig.cs) :

    { "ConfigVersion": "0.8.9", "Profiles": [ {
        "Emulator": "RetroArch", "Platform": "Sony Playstation",
        "Mode": "SmartExtract", "CacheSubDir": "", "Priority": "(Europe);(USA)",
        "ExtractCompanions": true, "CompanionExtensions": "bin",
        "FlattenExtraction": false, "ConvertAfterExtract": false,
        "Conversions": [ { "Input": "chd", "Output": "cue/bin" } ],
        "RomExtensions": "", "IgnoredExtensions": "" } ] }

Mode : SmartExtract / etc. ; Priority : tags pondérés de choix de ROM
("(Europe)" ou wildcard "*[!]*") ; Conversions : règles chdman/DolphinTool ;
CompanionExtensions : fichiers compagnons à extraire avec la ROM (bin pour cue).
Cas d'usage : préférer les dumps (Europe) et convertir les .chd en cue/bin pour
un émulateur qui ne lit pas le CHD.

--------------------------------------------------------------------------------
 game-suggester.json — règles de suggestion (Similar / Recommended / Ports)
--------------------------------------------------------------------------------
Écrit quand on édite les règles de scoring (GameSuggesterConfig.Save()).
Trois catégories, chacune : AllowDbGames (proposer des jeux hors bibliothèque),
MinimumScore, et une liste Criteria :

    { "Similar": { "AllowDbGames": false, "MinimumScore": 3, "Criteria": [
        { "FieldKey": "Genre", "UseGameValue": true, "Weight": 2 },
        { "FieldKey": "Platform", "ComparisonValue": "Arcade", "Weight": null } ] },
      "UseLbSimilarGames": true, "UseLbRecommendedGames": true }

Weight=null = FILTRE dur (obligatoire) ; sinon poids additionné au score.
UseLb* : fusionner avec les listes calculées par LaunchBox.
Cas d'usage : exiger le même genre (filtre) + bonus si même développeur.

Écrit par la page Parental (ParentalConfig). Le PIN N'EST PAS ici : c'est le

--------------------------------------------------------------------------------
 3.1 litebox-options.db — LE store par-entité (table options, EAV)
--------------------------------------------------------------------------------
    options(scope TEXT, entity_id TEXT, key TEXT, value TEXT,
            PRIMARY KEY(scope, entity_id, key)) WITHOUT ROWID

scope     : global | game | emulator | platform | playlist.
entity_id : GUID du jeu/émulateur ; NOM pour une plateforme (pas de guid LB) ;
            "" pour global.
key/value : une option posée = une row ; supprimer la valeur = SUPPRIMER la row
            (tri-state : pas de row = hériter du palier supérieur).

Toute clé doit être DÉCLARÉE dans Host/Data/OptionKeys.cs (scope autorisés,
type, cache Hot/Cold, propriétaire). Une clé inconnue est loggée en prod et
LÈVE sous --debug. Les clés Hot sont préchargées en RAM au boot (write-through);
les Cold lisent la base à la demande (chemins de lancement).

Registre actuel :
  scope global (routées "ProblemKeys" — en db SEULEMENT si le LaunchBox détecté
  est < 13.28, sinon partagées dans Settings.xml) :
    StartupScreenPostLaunchDisplayTime, ShutdownScreenPostReadyDisplayTime,
    ForceFrontendFocusOnShutdown, MonitorStartupShutdownWithProcess
  scope global (switchs de modules, row absente = défaut du module) :
    Module.base, Module.rom, Module.retroachievements, Module.parental,
    Module.web
  scopes game+emulator (overrides gameplay, §1.3 pour la sémantique ; édités par
  Edit Game / Edit Emulator → onglets LiteBox) :
    StartupStayOnTop, ExitScreenEagerMs, PauseHotkey, ScreenCaptureKey,
    PadPauseEnabled, PadPauseButton, PauseTarget, PauseFreezeTree,

Extrait code (résolution tri-state) — Host/Data/LiteBoxOption.cs :

    public static bool ResolveBool(string key, string emuId, bool globalValue,
                                   string gameId = null)
    {
        var g = GetOverride(ScopeGame, gameId ?? "", key);
        if (!string.IsNullOrEmpty(g)) return g == "true";
        var e = GetOverride(ScopeEmulator, emuId ?? "", key);
        return string.IsNullOrEmpty(e) ? globalValue : e == "true";
    }

--------------------------------------------------------------------------------
 3.2 LiteBox.pending.db — journal d'écriture vers les XML LaunchBox (ops)
--------------------------------------------------------------------------------
    ops(seq INTEGER PK AUTOINCREMENT, ts INTEGER, op TEXT, entity TEXT,
        id TEXT, parent_id TEXT, field TEXT, value TEXT)

Ce n'est PAS un stockage : c'est un tampon WAL. Chaque modification destinée aux
XML LaunchBox (favori, note, champ édité…) devient une op ordonnée ; le journal
est rejoué en mémoire au boot puis FLUSHÉ vers les XML quand c'est sûr (LB/BB
fermés), puis vidé. Exemple de row :

    12 | 1753576800000 | modify | Game | 81ad5a6f-… | | Favorite | true

op = modify/add/remove/entity-replace ; entity = Game / Emulator / Settings /
AdditionalApplication… ; parent_id pour les sous-entités. Reset intégral protégé
par PRAGMA user_version. Supprimer ce fichier = perdre les modifs pas encore
écrites dans les XML (et rien d'autre).

--------------------------------------------------------------------------------
 3.3 launch-history.db — dernier lancement par jeu (table launch_history)
--------------------------------------------------------------------------------
    launch_history(game_id TEXT PK, additional_app_id TEXT, emulator_id TEXT,
                   extracted_rom_path TEXT, last_launched_utc TEXT,
                   detection_ms INTEGER)

Une row par jeu : quelle version (additional_app_id), quel émulateur et quelle
ROM extraite ont servi au dernier lancement, quand, et combien de temps la
détection de fenêtre a pris (detection_ms alimente la barre de progression de
l'écran de démarrage). Sert à re-proposer le même choix sur le bouton Play et à
la correction RA au lancement. Exemple :

    81ad5a6f-… | NULL | retroarch-guid | R:\romcache\AB12CD34\game.z64
               | 2026-07-27T00:41:12Z | 5230

Écrit par RecordLaunch/RecordLaunchRomEntry (UPSERT — jamais INSERT OR REPLACE,
pour ne pas perdre detection_ms).

--------------------------------------------------------------------------------
 3.4 rom-archive-cache.db — listings d'archives + moteur RetroAchievements
--------------------------------------------------------------------------------
Entièrement RECONSTRUCTIBLE (re-scan / re-hash / re-téléchargement API).

  archive(signature PK, path, size, short_sig, cached_at, parse_state)
     Une row par ARCHIVE scannée. signature = clé portable du fichier (chemin
     relatif à LB + taille, 10 hex) ; parse_state = état du parse RA complet
     (0 à faire / 1 ok / 2 échec).
  archive_entry(signature, filename, path_in_archive, size,
                RetroAchievementsHash, RetroAchievementsId,
                PK(signature, path_in_archive))
     Une row par FICHIER contenu dans l'archive, avec son hash RA et le raid
     résolu. C'est ce qui permet d'afficher 🏆 par ROM dans le sélecteur.
  cache_entry(signature PK, game_title, platform, emulator, source_path, mode,
              output_file, size_bytes, cached_utc, last_played_utc)
     Manifeste du cache d'EXTRACTION : une row par dossier romcache\<SIG>\ —
     l'unité d'éviction LRU (last_played_utc).
  rom_hash(signature PK, path, size, RetroAchievementsHash,
           RetroAchievementsId, computed_at)
     Hash RA des ROMs "nues" (hors archive).
  ra_game(id PK, console_id, title, console_name, image_icon,
          num_achievements, num_leaderboards, points, date_modified,
          forum_topic_id)
     Catalogue RetroAchievements par console (API_GetGameList) : une row par
     jeu RA connu. Ex : 10078 | 2 | "Banjo-Kazooie" | "Nintendo 64" | … | 85 | …
  ra_hash(hash PK, game_id)
     Index inverse hash → id de jeu RA (hash en minuscules). C'est la table
     interrogée à chaque résolution ("ce hash correspond-il à un jeu RA ?").
  ra_console(id PK, key, name, games_refreshed_at, next_refresh_at)
     Planification du rafraîchissement du catalogue par console (backoff,
     garde anti-troncature).
